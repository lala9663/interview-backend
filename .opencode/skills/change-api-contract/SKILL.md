# API 계약 변경

계약은 세 레포가 함께 쓰는 약속이다. 원본은 프로젝트 공통 문서(`docs/03-api-contract.md`)이고,
이 레포의 `docs/contract/api-contract.md` 는 **복사본**이다. 복사본만 고치면 다른 두 레포와 어긋난다.

## 1. 먼저 판단한다: 정말 계약 변경인가

| 상황 | 계약 변경? | 할 일 |
| --- | --- | --- |
| 계약에 있는 경로의 내부 구현만 바꾼다 | 아니다 | 그냥 구현한다 |
| 계약이 모양을 안 정한 응답을 채운다(예: 대시보드) | 아니다 | `docs/open-questions.md` 3장에 정한 모양을 적는다 |
| 응답에 필드를 **추가**한다 | 그렇다(호환됨) | 아래 2장의 "추가" |
| 요청에 **선택** 필드·쿼리 파라미터를 추가한다 | 그렇다(호환됨) | 아래 2장의 "추가" |
| 새 경로를 추가한다 | 그렇다(호환됨) | 아래 2장의 "추가" |
| 열거형에 값을 추가한다 | 그렇다(**깨질 수 있음**) | 프론트·Agent 가 모르는 값을 받아도 죽지 않는지 확인 후 "추가" |
| 필드·경로 이름 변경, 삭제, 타입 변경, 필수화, 의미 변경 | 그렇다(**깨짐**) | 아래 3장의 "깨지는 변경" |
| 오류 코드 추가 | 그렇다(호환됨) | "추가". 프론트가 모르는 코드는 message 를 그대로 보여 주면 된다 |

판단이 애매하면 "깨지는 변경"으로 다룬다.

## 2. 호환되는 변경 (추가)

1. 변경안을 적는다: 무엇을(경로·필드·타입·예시 JSON), 왜, 영향받는 레포.
2. 세 레포 담당자에게 알리고 합의한다. **코드부터 고치지 않는다.**
3. 원본 문서를 고친다 → 같은 날 세 레포의 복사본(`docs/contract/api-contract.md`)을 갱신한다. 복사본 갱신은 그것만 담은 작은 PR 로 먼저 합친다.
4. 구현 순서는 아래 "배포 순서"를 따른다. 이 레포의 예:
   - 프론트가 쓸 응답 필드 → 백엔드가 먼저 내보낸다 → 프론트가 쓴다.
   - 백엔드가 쓸 Agent 응답 필드 → Agent 가 먼저 내보낸다 → 백엔드가 쓴다.
5. 이 레포에서 함께 고칠 것:
   - 프론트 ↔ 백엔드(2장): 해당 기능의 DTO·컨트롤러·테스트
   - 백엔드 → Agent(4장): `agent/dto/AgentDtos`, `HttpAgentClient`, `FakeAgentClient`, `HttpAgentClientTest`
   - Agent → 백엔드(5장): `internal/InternalDtos`, `InternalRoomController`, `CoreFlowIntegrationTest`

## 3. 깨지는 변경 (이름 변경·삭제·의미 변경)

한 번에 바꾸지 않는다. **추가 → 옮기기 → 삭제** 세 단계로 한다(아래 "배포 순서").

1. 새 이름(새 필드·새 경로)을 **추가**한다. 옛것도 계속 동작하게 둔다. 계약에 옛것을 "폐기 예정"으로 표시한다.
2. 쓰는 쪽(프론트 또는 Agent)이 새것으로 옮긴다.
3. 모든 쪽이 옮긴 것을 확인한 뒤 옛것을 지운다(계약에서도 지운다).

- 각 단계는 별도 PR 이다.
- 단계 사이에 덜 끝난 동작이 드러나면 안 되면 기능 플래그(`app.features.<이름>`) 뒤에 둔다.
- DB 컬럼 변경이 따라오면 `add-entity-and-migration` skill 의 5장(ALTER 문)도 따른다.

## 배포 순서 (세 레포 공통)

이 문단은 세 레포의 `change-api-contract` skill에 같은 내용으로 들어 있다. 고칠 때는 셋을 함께 고친다.

- **더하는 변경**(필드·경로·이벤트·오류 코드 추가): 어느 쪽이 먼저 나가도 되게 만든다. 받는 쪽은 그 값이 **없어도** 동작하고, **모르는 값이 와도** 무시한다. 그래도 순서를 정해야 하면 내보내는 쪽이 먼저다.
- **깨는 변경**(이름 변경, 삭제, 타입 변경, 필수화, 뜻 변경): 한 번에 바꾸지 않는다. 추가 → 옮기기 → 삭제 세 단계로 한다. 받는 쪽이 먼저 옛것과 새것을 모두 받게 하고, 그다음 보내는 쪽이 새것으로 바꾸고, 마지막에 옛것을 지운다.
- **열거형 값 추가**는 깨질 수 있다. 받는 쪽이 모르는 값을 받아도 죽지 않는지 먼저 확인한다.
- 계약 문서(원본과 세 복사본)는 같은 날 고친다. 코드는 위 순서를 지키면 같은 날이 아니어도 된다.

## 4. 하면 안 되는 것

- 이 레포의 복사본만 고친다.
- 구현하다가 편해 보여서 필드명·경로를 계약과 다르게 만든다.
- 계약의 필드를 응답에서 조용히 뺀다(값이 없으면 `null` 로 내보낸다).
- 열거형 값의 철자를 바꾼다(`NEW_GRAD` → `NEWGRAD`). DB 에 문자열로 저장돼 있다.
- 계약과 다르게 구현해 놓고 문서에 적지 않는다.

## 5. 계약을 못 바꾸는 상황이면

합의를 기다릴 수 없고 계약도 건드리면 안 되는 작업이면(자동 작업 등):

- 계약의 경로·필드는 그대로 구현한다.
- 꼭 필요한 추가만 **호환되는 형태**(선택 필드, 추가 필드)로 넣는다.
- 무엇을 추가했고 왜 필요한지 `docs/open-questions.md` 3장에 적고, 작업 보고에 "계약 변경 제안"으로 남긴다.

## 6. 체크리스트

- [ ] 세 레포 담당자가 합의했다
- [ ] 원본과 세 레포의 복사본이 같은 내용이다
- [ ] 내보내는 쪽이 먼저 배포된다. 받는 쪽은 없어도 동작한다
- [ ] 깨지는 변경은 추가 → 옮기기 → 삭제로 나눴다
- [ ] 이 레포의 DTO·Fake·테스트가 새 계약과 맞는다
- [ ] `./gradlew build` 통과
